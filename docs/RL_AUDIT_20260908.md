# RL(stage6 judge) audit — 2026-09-08

Offline audit of the hard4k v2 RL run (base = stage6 ck250) using the raw scored
shards already on disk (no GPU needed). Reproduce with:

    python scripts/rl_eval_audit.py --report \
      output/benchmarks_stage6/stage3/checkpoint-250 \
      output/bench_rl_t2i/step60 output/bench_rl_t2i/step340 output/bench_rl_t2i/step360 ...

## 1. Base attribution (was "未跑") — ANSWERED

* stage6 ck250 eval outputs (same 3-dim-v2 protocol as the RL evals): **99.5% pure
  3-dim**, zero Physical Plausibility / World Knowledge / Text Rendering labels.
* RL outputs show the non-canonical taxonomy **from the very first checkpoint
  (step 60, ~82% of outputs) and stay ~85% through step 420**.

=> The "4-dim / Physical Plausibility" drift is **introduced by RL, not present
   in the SFT base**. Root cause: the mean_threshold reward never constrains the
   checklist schema, so the model relaxes back to the older stage3-5 taxonomy
   that the (pre-10:39) system prompt still primed with those words.

## 2. The "~10% runaway" is a repetition loop, NOT verbosity

Truncated RL outputs (no `final_score`, cut at the token cap):
* median **~100** `eval_points`, but median **distinct-question ratio ~0.11**
  (i.e. ~89% of the text is the same question repeated ~dozens of times).
* They are pure self-repeat attractors; they **never emit `final_score`**.

Terminating RL outputs (the kept set) max out at p95 ≈ 3.9k chars / max ~10k
chars — i.e. **no legitimately-terminating output is close to the 4096 cap**.

=> **Raising max_new_tokens to 8192 recovers ≈ 0 pairs.** Every excluded pair is
   a loop; a bigger budget just produces more repeats and still no `final_score`.
   A plain 8192 rerun will return essentially the same table (only slower).
   Rescuing the loops needs generation-time repetition control
   (frequency/presence penalty, no_repeat_ngram) and even then the recovered
   judgments are on degenerate outputs.

## 4. Recommendation

1. Do **not** spend GPU time on a plain 8192 rerun of these steps expecting to
   recover coverage — it won't (see §2).
2. The two options that would actually move the needle:
   * **(A) eval-time rescue experiment (cheap)**: rerun RL steps 340/360/420 with
     vLLM repetition control (e.g. `frequency_penalty≈1.0–1.5`) to break the
     loops and get a genuine **full-set** accuracy. This is the only way to know
     if the +3pt on genai survives once the loop pairs are forced to answer.
   * **(B) retrain (the robust fix)**: stage6 ck250 → GRPO with the improved
     recipe — reward adds a **dimension whitelist penalty** (3-dim only) and a
     **length/termination penalty** (hard cap on eval_points, penalize
     non-termination), LoRA **excludes linear_attn**, system prompt = the
     de-primed 10:39 version. Small-step validation first (~200–300 steps),
     evaluate at the same settings incl. repetition control for a fair table.
3. Net view on the decision point: don't ship RL 340/360 as-is yet — schema is
   dirty and the +3pt is on a biased 80–84% subset; base stays the clean
   reference. If a full-set (repetition-controlled) eval shows RL still beats
   base on genai without losing mmrb2, that justifies the retrain; otherwise
   staying on stage6 is defensible.

## 5. Code deliverables (prepared 2026-09-08, all default-off / backward compatible)

* `scripts/rl_eval_audit.py` — offline audit of any step/base dir (taxonomy
  drift, truncation/repetition-loop, acc/tie). 
* `scripts/eval_stage3.py` + `scripts/eval_benchmarks_stage3.py` — new optional
  `--frequency-penalty/--presence-penalty/--repetition-penalty/--no-repeat-ngram-size`
  forwarded to ms-swift `RequestConfig` (degrading gracefully if unsupported).
* `scripts/run_rl_bench.sh` / `run_rl_bench_all.sh` — plumb `EVAL_FREQUENCY_PENALTY`
  etc. and a `BENCH_SUFFIX` so the repetition-controlled rerun writes to its own
  tree (`output/bench_rl_t2i_rp/`) without clobbering the baseline.
* `RM_RL-main/.../pairwise_image_edit_reward_manager.py` — new config knobs:
  `allowed_dimensions` (eval_points label whitelist; defaults to `dimensions`
  when set, empty => no enforcement), `strict_summary` (summary keys must be
  exactly the required dims), `dimension_penalty`, `invalid_rollout_penalty`
  (explicitly negative reward for non-terminating/truncated rollouts). All
  default to prior behavior (image-edit example unaffected).
* `RM_RL-main/examples/reward_function/run_t2i_stage6_rl_v3.sh` — v3 retrain
  wrapper: reproduces the v2 rollout/model config, adds the reward guards above
  + `max_checkpoint_count` cap, and excludes `gdn`/`linear_attn` from LoRA
  (`exclude_modules=.*visual.*|.*gdn.*|.*linear_attn.*`). Verify after the first
  merge that no linear_attn/gdn LoRA deltas remain
  (`scripts/delta_check.py --base ... --merged ...`).
